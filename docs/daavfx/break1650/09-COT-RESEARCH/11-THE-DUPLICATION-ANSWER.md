# 11-THE-DUPLICATION-ANSWER - the operator's question, answered with our data

The question (2026-10-24): "if the LLM thinks a long block and then replies
with things derived from it, is that DOUBLE TOKENS, or does the harness
itself already do what I'm thinking - try not to duplicate words already
typed by the reasoning? does it RECALCULATE ALL or is it a simple reply once
thought?"

## The mechanical answer (three levels)

**Level 1 - within the model: no duplication, no recalculation.**
The answer tokens are generated once, in the same stream, after the thinking
tokens. The thinking tokens' KV is in the cache; every answer token ATTENDS
to them at a fraction of the cost of computing them. The model never
re-tokenizes, re-reads, or re-does its own thinking. What feels like
duplication to an observer is the model's *behaviour*: it often restates the
conclusion it reached. That is wasted OUTPUT text (a training habit), not a
mechanical double computation.

**Level 2 - across turns: duplication is happening, and it is our harness's
fault.** Every turn our driver resends the whole rendered dialogue, so the
server re-prefills everything: the tool catalog, the task, all prior turns,
all prior thinking. Measured on qwen3.5-4b r2: **104,499 prompt tokens
against 17,803 completion tokens**. That is 5.9x. If the prefix stayed
byte-identical across turns, the server's slot matching would reuse the KV
and each turn would pay only the new delta - which on this box (prefill at
0.14-0.39 t/s!) would be the single biggest wall-clock win available.

**Level 3 - and it currently doesn't.** Our driver appends only the assistant
CONTENT to history (not the reasoning), so the re-rendered prompt differs
from the byte sequence the model actually generated. Prefix identity breaks
at the end of every turn's thinking; the cache misses; full re-prefill.

So the honest scorecard for "does the harness already avoid duplicating?":

| Duplication mode | Happens today? | Where |
|---|---|---|
| Model re-does its own thinking mechanically | NO - KV reuse handles it | research/04 |
| Model restates its conclusion as the answer | YES - behavioural waste, part of the 77% | 08-THINKING-DEEP-DIVE |
| Harness re-prefills the full history each turn | YES - **the biggest single cost on the bench** | 10-MECHANICS |
| Reasoning tokens blocking cross-turn prefix reuse | YES - history omits reasoning from the rendered text | 10-MECHANICS |

## The fixes this unlocks (all keep reasoning; none disable it)

| Fix | Mechanism | Expected effect |
|---|---|---|
| **R1 - prefix fidelity** | append the assistant turn INCLUDING the reasoning channel so the rendered prompt matches the generated bytes | slot reuse starts hitting; per-turn prefill collapses to the delta |
| **R2 - persistent session proxy** | a thin proxy holding one persistent request per bench run, sending only increments (llama.cpp has no slot persistence, verified) | prefill cost becomes O(delta) per turn instead of O(history) |
| **R3 - shared-prefix awareness** | keep the system prompt + task payload byte-stable across runs; tokenize once | repeated identical runs reuse their prefix |
| **R4 - thinking-aware reuse policy** (from research/05) | at temp 0, thinking is deterministic: for identical repeated prompts the thinking block IS reusable - our A/B harness reruns are exactly that case | repeated harness iterations skip thinking prefill entirely |
| **R5 - behavioral de-duplication** | measure reasoning-to-answer restatement overlap in our transcripts; if high, tighten the response format so the model does not repeat itself | shrinks the 77% at the source |
| **R6 - draft the thinking** (from research/04's acceptance-rate logic) | speculative decoding over reasoning segments on the iGPU theater | makes the 77% cheaper, not smaller |

R1/R2 are bench-side changes (my lane), R5/R6 are the P1 experiments. None
of them touches whether the model thinks.

## The one-line answer for the record

The model does not double-compute its thinking - the KV cache already does
exactly what the operator intuited ("reuse what was computed"). What our
stack actually does is re-prefill 5.9x more tokens than it generates, and
that is a harness bug class, not a physics wall.
